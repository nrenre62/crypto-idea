# PR Workflow — how CryptoIdea writes pull requests

**Canonical standard for every pull request in this repo** — hand-written or produced by the
Agent Factory. Distilled from the founder's research note *"PR Explained"* and adapted
to this repo's real conventions (Jira project **CRYP**, `claude/…` feature branches, the
server-side CI in `.github/workflows/ci.yml`). Sibling to [`AGILE.md`](AGILE.md) and
[`JIRA-WORKFLOW.md`](../testing/JIRA-WORKFLOW.md); see also the [docs hub](../INDEX.md).

> **North star.** A PR is a reviewable proposal to merge one branch into `master`, and its whole
> point is the reviewer's experience. Make each PR **small, single-purpose, and self-explanatory**
> so anyone — a future hiring manager included — can understand it in a few minutes.

## The rule in one line

**One PR = one task = one Jira card.** Branch (`claude/…`) → Conventional-Commit commits → push →
open a PR that fills the template and links the ticket → self-review the diff → CI green → **squash-
merge → delete branch.** Keep it under **~200 changed lines**; split if it grows.

**Every planning session opens a NEW PR (founder rule).** A new plan → a fresh branch off
the latest `master` → a **new** PR. **Never** push to `master`. **Never** push to, reuse, or
force-push/rewrite an **old** PR (merged or closed) or its branch — a merged/closed PR is finished.
Follow-up or corrective work restarts the branch from the latest `master` and opens a **new** PR.

## 1. Branch

- Agent + web/remote work stays on **`claude/…`** feature branches (the CI triggers on `claude/**`,
  and the remote environment auto-creates them). The branch name barely matters — squash-merge
  deletes it and it never appears in `master`'s history. **The PR title is what survives**, so put
  the discipline there, not in the branch name.
- Never commit straight to `master`.
- **One plan = one fresh PR (founder rule).** Every planning session branches anew off the
  latest `master` and opens a **new** PR. Never push to, reuse, or rewrite/force-push an **old**
  (merged or closed) PR or its branch — that history is finished. Follow-up work is a *new* branch and a
  *new* PR restarted from the latest `master` (this is why the branch name barely matters: each plan
  gets its own).

## 2. Title — a Conventional-Commit line

One concise line describing *what the change does*, prefixed with the Conventional-Commit type, with
the Jira key in parentheses. After a squash-merge, `git log` on `master` reads like a changelog.

- ✅ `fix(portfolio): prevent NaN in total when a holding has no price (CRYP-142)`
- ✅ `feat(journal): add CSV export of theses (CRYP-88)`
- ❌ `Fix bug` · `update` · `changes`

Types: `feat` · `fix` · `chore` (deps/maintenance) · `docs` · `refactor` (no behavior change) ·
`style` · `test` · `perf` · `build` · `ci`. A refactor gets its **own** PR, never mixed with a
behavior change.

## 3. Body — fill the template, answer three questions

Every PR body fills [`.github/pull_request_template.md`](../../.github/pull_request_template.md):

1. **Why** — the context and the problem. Link the ticket: `Jira: CRYP-___`, and `Closes #___`
   for the GitHub issue (see §7).
2. **What changed** — a bullet list of the specific changes.
3. **How I tested it** — the exact tiers/steps you ran and the result (`test:unit` / `test:rules` /
   `test:integration`, a build, a manual click-through). Be specific; "tested" alone says nothing.
4. **Screenshots / GIF** — required for any UI change (before/after); delete the section if N/A.
5. **Checklist** — the three-item self-review gate.

The attribution footer (`_Generated by Claude Code_` / `🤖 Generated with Claude Code`) is appended
by the harness per PR — **do not hard-code it** into the template or the body (the server strips
duplicates).

## 4. Size — the ~200-line ceiling

Small atomic PRs get reviewed faster and more thoroughly, introduce fewer bugs, and roll back
cleanly (Google eng-practices; the SmartBear/Cisco study found defect-finding collapses past
~400 lines). **Aim under ~200 changed lines and a handful of files. If a task grows past ~200–400
lines or sprawls across many files, STOP and split it** (e.g. data-model change in one PR, UI
wiring in the next). Spread matters as much as count: 200 lines in one file can be fine; the same
change across 50 files is too big.

## 5. Self-review before requesting review

Always read your **own** diff in the *Files changed* tab first — catch stray `console.log`s,
accidental file changes, and typos before anyone else's time is spent. In the factory this is
backed by the read-only reviewer agents (`secure-by-design` / `design-consistency` /
`consistency-sweep`), but the human/orchestrator self-read still happens.

## 6. CI green before merge

`.github/workflows/ci.yml` runs on every PR to `master` and reports three independent checks:

- **`build + unit tests`** — `npm run build` (vite + SW stamp + no-names dist guard) + `npm run test:unit`
- **`rules tests (firestore emulator)`** — `npm run test:rules` (the `firestore.rules` security boundary)
- **`integration tests (auth+firestore+functions emulators)`** — `npm run test:integration` (real callable bodies)

**Never merge with a red or pending Checks tab.** A red CI is a real failure — fix it and push,
don't merge around it.

## 7. Linking issues & tickets

- **Jira (CRYP):** put the key in the PR title and body. The Jira/GitHub integration links them for
  traceability; Jira does **not** auto-close from GitHub keywords — the ticket is transitioned in
  Jira (see [`JIRA-WORKFLOW.md`](../testing/JIRA-WORKFLOW.md)).
- **GitHub issues:** open a GitHub issue per task and close it from the PR with `Closes #NN`
  (keywords: `close/closes/closed`, `fix/fixes/fixed`, `resolve/resolves/resolved`) — these
  auto-close the issue when the PR merges into `master`, leaving the issue-to-PR trail. Use the
  Jira key for the tracker of record and the GitHub issue for the public history.

## 8. Merge — Squash and merge, then delete the branch

- **Squash and merge** collapses the branch's (possibly messy, AI-iterated) commits into **one
  changelog-quality commit** on `master`. This is the repo's merge method — the branch can be messy,
  `master` stays clean.
- **Delete the head branch** right after merge (GitHub offers the button; auto-delete is enabled).
- Solo, **self-review then merge your own PR** — that's expected and fine. Do not fake approvals or
  add branch protection that blocks yourself.

## 9. Draft PRs

Open as a **draft** while work is in progress: it can't be merged, but the diff is visible and
commentable. Click **Ready for review** when done. Useful for parking work-in-progress.

## 10. Repo settings (one-time, GitHub UI — not code)

These are set in the GitHub web UI (no API path from the agent environment):

- **Settings → General → Pull Requests:** set **Squash and merge** as the default, **disable**
  Merge-commit and Rebase, and enable **"Automatically delete head branches."**
- **Settings → Branches → Branch protection (`master`):** require a PR before merging and require the
  status checks above (`build + unit tests` at minimum; add the two emulator checks once you've
  watched a few runs go green). With protection on, GitHub blocks self-approval — that's a team
  control; solo, keep protection to "require checks," not "require review."

## 11. How the Agent Factory applies this

The factory ([`AGENT-FACTORY.md`](AGENT-FACTORY.md)) **opens a PR per component by default** at gate
**G3** (founder standing decision — this supersedes the old "no PR unless asked"). The
flow: `integrator` commits with a Conventional-Commit message + the `Co-Authored-By` trailer and
pushes to the `claude/…` branch (step 16); at **G3** the orchestrator **opens the PR** — title per §2,
body filling the template per §3, the CRYP key + `Closes #` per §7 — presents the PR link + diff +
green verdict, and asks the founder (plain chat) to approve the **squash-merge**. The founder still
decides the merge; only the *opening* of the PR is now automatic.
