### S03-01 · High · "Empty trash" (and "Delete now") permanently erases an account that is no longer in the Trash — the server's `deleteUser` never checks `deleted:true`, and the client purges from a stale list
- **Steps to reproduce (run 1, 19:44–19:45):** 1) As owner admin2, Users → move qa-adm-02 and qa-adm-03 to the trash; open the Trash tab (shows both). 2) In the user app, log in as qa-adm-02 → "Your account is scheduled for deletion" → **Restore my account** (17:44:50Z) → normal app, account active again (`deleted:false`). 3) Back in the still-open admin Trash tab (not refreshed) click **Empty trash**, type DELETE → the button reads **"Delete 2"** → click.
- **Run 2 (19:46, server only):** qa-adm-31 registered with one coin and **never trashed**; from the signed-in admin2 panel `deleteUser(uid)` (the same callable "Delete now" / "Empty trash" use) → resolved, Auth record + user doc + portfolio + coin erased. The server has no "must be in the trash" check at all.
- **Run 3 (19:47, single "Delete now"):** qa-adm-32 → Move to trash → Trash tab open → user clicked "Restore my account" in its tab (17:47:25Z, account active) → in the stale Trash tab "Delete now" + DELETE → "Permanently deleted ✓" (17:47:34Z), account gone.
- **Run 4 (resumed run, 21:41, keyboard-only):** qa-adm-52 (BTC + 1 buy) → Move to trash → Trash → Refresh → Tab to its **Delete now** → Enter → type DELETE → Tab → focus on **OK** → in the user tab qa-adm-52 clicks **Restore my account** (Firestore `deleted:false` verified) → Enter on OK in the admin tab → "Permanently deleted ✓": user doc 404, Auth `EMAIL_NOT_FOUND`, its 5 `rateLimits` docs survive (S07-08). The restored user's open tab kept showing "0.01 BTC · $598.13" (cached) after its account was erased.
- **Expected:** only accounts that are *currently* in the trash are purged; qa-adm-02, restored a minute earlier, survives (or the purge refuses with "this account is no longer in the trash").
- **Actual:** both were erased (17:45:08Z): no Auth record, no `users/{uid}` doc, no portfolios/coins for qa-adm-02. Its open user tab silently flipped to an empty "No coins yet" portfolio with no notice. Trash then reads "Trash is empty."
- **Root cause (code):** `src/hooks/useAdminDashboard.js` `emptyTrash(uids)` loops over the uids captured from the cached `userList` (`src/components/admin-dashboard.jsx` ~line 1094 `trashedNow.map(u => u.uid)`), and `functions/index.js` `exports.deleteUser` (~line 1444) erases ANY non-owner uid — it never reads `users/{uid}.deleted`. The UI promise "Permanent erasure (GDPR/CCPA) happens only from the Trash tab" is a client-side convention only. The same applies to a single **Delete now** row and to any stale second admin tab (another admin, or the user themself via "Restore my account", restores the account → it is still purged).
- **Effect on user accounts / user app:** irreversible loss of an ACTIVE user's whole account and data (portfolios, coins, transactions, theses) — the exact thing the 30-day trash exists to prevent. The user is not told; their open session just shows an empty book.
- **New** (related: S01-07 / S06-08 let a user restore from the trash; S08-01 is the reverse direction).
- **Suggested fix:** in `functions/index.js` `deleteUser`, read `users/{uid}` first and refuse unless `deleted === true` (`failed-precondition`, "This account is no longer in the trash — refresh"), optionally with an explicit `{force:true}` for a deliberate GDPR erasure of an active account. In `emptyTrash`, re-fetch the list (or send the uids and let the server skip non-trashed ones) and report "Purged N, skipped M (restored since)".
